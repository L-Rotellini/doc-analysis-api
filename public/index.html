Comment ça marche ? le découplage producteur / consommateur, en 4 temps ▾
01
Réception

L'API POST /requests insère la demande en pending via Kysely, puis répond 202 Accepted immédiatement.

02
Mise en file

Un job est déposé dans Redis via BullMQ. La requête HTTP est déjà terminée — le client n'attend pas.

03
Traitement

Un worker séparé consomme le job et simule l'analyse (~2 s). On peut le scaler indépendamment de l'API.

04
Persistance

Le worker passe la ligne en analyzed. La page poll GET /requests chaque seconde et fait flasher la carte.

Deux sources de vérité. La liste reflète l'état métier en base (pending / analyzed). Le pipeline et le statut worker viennent de BullMQ (getJobCounts + getWorkers) — l'état d'exécution n'est pas persisté en base. L'état « en cours » d'une carte est dérivé côté client à partir de stats.active.

Pause ≠ hors ligne. Pause appelle analysisQueue.pause() : la file arrête la distribution, mais le worker reste connecté (le job en cours finit, les nouveaux s'empilent en waiting). C'est la primitive de maintenance. « Hors ligne » indique au contraire qu'aucun process worker n'est connecté (heartbeat absent ; peut prendre quelques secondes à apparaître).
